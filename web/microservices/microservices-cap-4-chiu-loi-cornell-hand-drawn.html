Chịu lỗi (resilience)

B chậm hoặc chết thì A không được chết theo

4Chịu lỗi

Q1 B chậm hoặc chết, A làm gì? Kể theo thứ tự các lớp phòng thủ. từ khóa: timeout · retry · circuit breaker · bulkhead · fallback

① Timeout trước, rồi các lớp sau

Hiểu nôm naGọi điện bạn mãi không bắt máy thì sau một lúc mình cúp, thử lại vài lần, rồi thôi và làm việc khác.

Bên dướiMọi network call bắt buộc có timeout, không có thì request treo và pool cạn. Timeout tầng dưới nhỏ hơn tầng trên; truyền deadline còn lại xuống (deadline propagation). Sau đó: retry (có kiểm soát) → circuit breaker → fallback (cache cũ, giá trị mặc định); bulkhead tách pool theo từng downstream.

Ví dụGateway timeout 3s, Order → Payment timeout 2s, Payment → đối tác timeout 1s: mỗi tầng còn dư thời gian để trả lỗi.

⚠ BẫyQuên timeout là lỗi kinh điển. Nói được thứ tự các lớp mới đạt, không chỉ nói “retry”.

Tự kiểmTimeout tầng dưới lớn hơn tầng trên thì chuyện gì xảy ra? (Tầng trên bỏ cuộc mà tầng dưới vẫn chạy tốn tài nguyên.)

Q2 Retry thế nào mới đúng? Khi nào không được retry? từ khóa: exponential backoff · jitter · transient error · retry storm

② Thử lại có kỷ luật

Hiểu nôm naGõ cửa nhà bạn không ai mở thì đợi một chút rồi gõ lại, chứ đứng đập cửa liên tục sẽ làm phiền cả xóm.

Bên dướiChỉ retry lỗi tạm thời (timeout, 503, connection reset), không retry 4xx. Exponential backoff (100ms → 200 → 400) kèm jitter (ngẫu nhiên) để các client không retry cùng lúc. Giới hạn số lần. Và chỉ retry thao tác idempotent (xem ④).

Ví dụRetry storm: 3 tầng × 3 lần retry = 27 request dội xuống B đang yếu.

⚠ BẫyRetry không idempotent (POST trừ tiền) là trừ tiền nhiều lần. Retry ở mọi tầng sẽ nhân lên.

Tự kiểmLỗi 400 “thiếu trường amount” có retry không? (Không, retry mãi vẫn lỗi.)

Q3 Circuit breaker hoạt động ra sao? từ khóa: closed / open / half-open · fail fast

③ Cầu dao tự ngắt

Hiểu nôm naĐiện chập thì cầu dao nhảy để khỏi cháy nhà. Một lúc sau thử bật lại, ổn thì dùng tiếp.

Bên dướiClosed —lỗi vượt ngưỡng→ Open —hết thời gian chờ→ Half-open —thử OK→ Closed, thử lỗi→ Open. Open = fail fast, không gọi B nữa: B có thời gian hồi, A không tốn tài nguyên chờ. Kèm fallback. Node: thư viện opossum.

Ví dụPayment lỗi 50% trong 10s → breaker mở, 30s sau cho 1 request thử. Thử OK thì đóng lại.

⚠ BẫyBreaker không thay timeout; chúng bổ sung nhau. Bulkhead chống một downstream chậm ăn hết cả pool.

Tự kiểmBreaker đang Open thì request đến sẽ đi đâu? (Trả lỗi hoặc fallback ngay, không gọi B.)

Q4 ⭐ Client retry API trừ tiền, làm sao không trừ 2 lần? Hai request trùng đến cùng lúc thì sao? từ khóa: idempotency · idempotency key · unique constraint · SET NX

④ Một chìa cho một lần làm

Hiểu nôm naPhiếu thu có số. Nhận lại đúng phiếu đã đóng dấu thì không thu tiền lần nữa mà đưa lại biên lai cũ.

Bên dướiIdempotent = gọi N lần cho kết quả như gọi 1 lần. GET/PUT/DELETE idempotent theo HTTP; POST thì không. Client gửi idempotency key; server lưu (key → response), request trùng thì trả lại response cũ. Lưu ở Redis có TTL hoặc bảng DB có unique index.

Ví dụHai request cùng key đến đồng thời: dùng SET NX hoặc unique index để chỉ một request thắng, request kia nhận “đang xử lý”.

⚠ Bẫy“Check rồi mới insert” bị race condition. Bước chiếm key phải nguyên tử.

Tự kiểmApp timeout rồi retry cùng key, lần 1 đã trừ tiền thành công: server trả gì? (Response cũ, không trừ lần hai.)

Q5 Vì sao một service chậm làm sập cả hệ? từ khóa: cascading failure · deadline propagation · load shedding

⑤ Chậm còn nguy hơn chết

Hiểu nôm naMột người đứng chắn cửa quá lâu thì cả hàng phía sau dồn lại, rồi hàng nối đến cả con phố.

Bên dướiB chậm → A giữ kết nối chờ → A cạn tài nguyên → C gọi A cũng chậm → lan ra cả hệ. Node: event loop không bị block nhưng pending promise, socket, memory dồn lên → OOM, latency tăng vọt. Chặn bằng timeout + circuit breaker + load shedding (quá tải thì từ chối sớm bằng 503) + rate limit.

Ví dụService B chậm 10s, A có 1000 request đang chờ B → A hết socket, mọi API của A đều lỗi, dù phần lớn không liên quan B.

⚠ BẫyĐừng nghĩ Node “không sợ” vì đơn luồng: tài nguyên bên ngoài event loop vẫn cạn.

Tự kiểmVì sao từ chối sớm (503) lại tốt hơn cố xử lý hết mọi request?

Summary

Thứ tự phòng thủ: timeout → retry (backoff + jitter, chỉ lỗi tạm thời) → circuit breaker → fallback, thêm bulkhead. Retry chỉ an toàn khi thao tác idempotent, nên API trừ tiền cần idempotency key (unique constraint / SET NX). Một service chậm làm cạn tài nguyên rồi lan dây chuyền; chặn bằng timeout, breaker, load shedding.
