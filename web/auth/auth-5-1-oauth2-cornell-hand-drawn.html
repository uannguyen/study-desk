Q1 OAuth2 giải quyết bài toán gì? Có những vai nào? từ khóa: delegation · resource owner · client · authorization server · scope

5.1 OAuth2 = ủy quyền, không đưa password

Nôm naTới nhà hàng, bạn đưa nhân viên giữ xe chiếc “chìa phụ”: nổ máy, lái vào bãi được, nhưng không mở cốp. Bạn không đưa chùm chìa chính.

ChốtCho app khác làm một việc thay bạn mà không thấy password: app nhận access token giới hạn bằng scope, có hạn, thu hồi được.

Ví dụApp in ảnh xin đọc Google Photos của bạn:
VaiTrong ví dụ
resource ownerbạn, chủ của ảnh
clientapp in ảnh, muốn làm thay bạn
authorization serverGoogle Accounts, nơi bạn bấm “Đồng ý”
resource serverGoogle Photos API, nơi giữ ảnh
Token scope=photos.read đọc ảnh→✓
Cùng token đó xoá ảnh / đọc Gmail→✗ ngoài scope
Áp dụngXin scope tối thiểu. Token giữ ở backend, không đưa xuống trình duyệt nếu không cần.

⚠ BẫyOAuth2 không phải giao thức đăng nhập. Biết “ai đang dùng app” là việc của OIDC (5.2).

Tự kiểmApp kế toán xin đọc Gmail để lấy hoá đơn: client là ai, resource server là ai? (app kế toán; Gmail API)

Q2 ⭐ Authorization Code flow chạy thế nào, từng bước? từ khóa: /authorize · redirect_uri · code · state · /token · back channel

5.1.1 Authorization Code: đổi phiếu lấy chìa

Nôm naBạn tới quầy lễ tân (Google) xác nhận, lễ tân đưa bạn một phiếu nhỏ mang về cho app. App cầm phiếu đi cửa sau đổi lấy chìa thật.

ChốtTrình duyệt chỉ mang code (phiếu dùng một lần, sống ngắn). Backend đổi code lấy token qua kênh sau. Token không đi qua URL.

Ví dụ
  1. App chuyển trình duyệt tới /authorize?client_id…&redirect_uri…&scope…&state=xyz
  2. User đăng nhập ở Google, bấm “Đồng ý”.
  3. Google redirect về redirect_uri?code=abc&state=xyz.
  4. Backend app POST /token gửi code (+ secret hoặc verifier) → nhận access token.
Áp dụngKiểm state lúc nhận callback (chống CSRF đăng nhập). Đăng ký redirect_uri chính xác, server so khớp tuyệt đối.

Q3 PKCE là gì, chống được gì? từ khóa: code_verifier · code_challenge · S256 · public client

5.1.2 PKCE: code bị trộm cũng vô dụng

Nôm naXé đôi tấm vé: đưa lễ tân một nửa, tự giữ nửa kia. Lúc nhận chìa phải ráp khớp hai nửa; ai nhặt được phiếu mà không có nửa vé thì không nhận được chìa.

ChốtApp sinh chuỗi bí mật verifier, gửi hash của nó (challenge) ở bước 1; lúc đổi code ở bước 4 phải trình verifier gốc.

Ví dụ
verifier = chuỗi ngẫu nhiên→challenge = SHA-256(verifier)→/authorize kèm challenge
/token kèm verifier→server hash lại, so→✓ khớp
Kẻ gian trộm code, không có verifier→✗
Áp dụngMobile và SPA (không giấu được client secret) bắt buộc PKCE; RFC 9700 khuyến nghị cho cả client có backend. Dùng thư viện (AppAuth, oidc-client-ts), đừng tự viết.

Tự kiểmPKCE dùng lại viên gạch nào ở mục 2? (hash 2.1: challenge = SHA-256 của verifier)

Summary

OAuth2 là ủy quyền: client nhận access token giới hạn theo scope mà không thấy password. Có user thì dùng Authorization Code: trình duyệt chỉ mang code, backend đổi code lấy token, kiểm state chống CSRF, thêm PKCE để code bị trộm cũng vô dụng.

Nguồn: RFC 6749, RFC 7636 (PKCE), RFC 9700 (OAuth 2.0 Security BCP). Trước: 5.0 Tổng quan · Tiếp theo: 5.2 OIDC.
