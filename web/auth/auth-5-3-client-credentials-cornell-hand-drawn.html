5.3 Client Credentials: máy gọi máy

Nôm naXe chở hàng của công ty có thẻ ra vào riêng, không cần nhân viên nào ký giấy mỗi lần ra cổng.

ChốtKhông có người bấm đồng ý → service tự xác thực bằng client_id + secret, nhận access token theo scope của chính service.

Ví dụ
POST /token
grant_type=client_credentials&client_id=order-svc
&client_secret=…&scope=payment.charge
→ { "access_token": "…", "expires_in": 300 }
Áp dụngCache token tới gần hết hạn rồi mới xin lại. Mỗi service một client riêng, scope tối thiểu, secret để trong secret manager.

⚠ BẫyToken này không đại diện cho user nào; không có refresh token.

Tự kiểmCron job đối soát gọi API payment lúc 2h sáng: dùng flow nào? (Client Credentials)

Q2 Vì sao Implicit flow bị bỏ? SPA dùng flow nào? từ khóa: implicit grant · URL fragment · password grant · RFC 9700

5.3.1 Flow đã bỏ: Implicit và Password

Nôm naLễ tân ném chìa thật qua cửa sổ ra đường lớn thay vì đưa phiếu: ai đứng gần cũng nhặt được.

ChốtImplicit trả token thẳng trên URL → lộ qua history, extension, Referer. Password grant bắt app cầm password của user. RFC 9700 bỏ cả hai.

Ví dụ
Implicit: redirect …/cb#access_token=eyJ…→✗ token nằm trên URL
Hiện nay: SPA, mobile→✓ Authorization Code + PKCE
Áp dụngGặp hệ cũ dùng Implicit → đề xuất chuyển sang Code + PKCE. SPA muốn chặt hơn thì thêm BFF: backend nhỏ giữ token, trình duyệt chỉ giữ cookie.

Tự kiểmSPA không có backend thì dùng flow nào? (Authorization Code + PKCE)

Summary

Không có user thì dùng Client Credentials: service tự xác thực bằng client_id + secret, nhận token theo scope của chính service. Implicit và Password grant đã bỏ: SPA và mobile đều dùng Authorization Code + PKCE.

Nguồn: RFC 6749, RFC 9700 (OAuth 2.0 Security BCP). Trước: 5.2 OIDC · Tiếp theo: 6 Chỗ hay thủng (OWASP).
