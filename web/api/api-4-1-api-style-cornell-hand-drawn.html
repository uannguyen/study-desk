4.1 · API style: REST, gRPC, GraphQL, webhook

Cách chia nghiệp vụ thành lời gọi: tài nguyên, hàm, truy vấn, sự kiện

1REST và RPC

Q1 ⭐ REST thật sự là gì? API thế nào thì gọi là RESTful? từ khóa: resource · HTTP method · status code · stateless · idempotent

Danh từ trong URL, động tác là method

Nôm naTủ hồ sơ có nhãn: mỗi ngăn một loại giấy tờ. Muốn gì thì nói động tác (xem, thêm, sửa, xoá) cộng tên ngăn.

ChốtREST là một style (Roy Fielding, 2000), không phải protocol. URL là danh từ (tài nguyên), động tác là HTTP method, kết quả là status code, server không giữ trạng thái phiên giữa các request (stateless).

Ví dụ
ViệcRESTKiểu RPC qua HTTP
Xem đơnGET /orders/42POST /getOrder
Tạo đơnPOST /orders → 201POST /createOrder
Huỷ đơnPOST /orders/42/cancelPOST /cancelOrder
Áp dụng
  • GET, PUT, DELETE là idempotent: gọi lại cho cùng kết quả → retry an toàn. POST thì không → retry thanh toán cần Idempotency-Key.
  • Lỗi trả đúng 4xx (client sai) hoặc 5xx (server lỗi), đừng trả 200 kèm {"error": …}.

⚠ Bẫy“Dùng HTTP + JSON là REST.” Nhiều API thật ra là RPC qua HTTP (POST /doSomething). Không sai, nhưng khi phỏng vấn nên gọi đúng tên.

Tự kiểmPUT và POST khác gì về idempotency? (gửi lại PUT cùng body → cùng trạng thái; gửi lại POST → có thể tạo hai bản ghi)

Q2 ⭐ gRPC khác REST thế nào? Khi nào chọn gRPC? từ khóa: RPC · Protobuf · .proto · HTTP/2 streaming · gRPC-Web

Gọi hàm từ xa theo hợp đồng in sẵn

Nôm naREST như viết thư tay theo ý mình. gRPC như điền mẫu đơn in sẵn ô: hai bên đã thống nhất ô nào ghi gì, đọc rất nhanh nhưng người ngoài nhìn vào khó hiểu.

ChốtgRPC là RPC: gọi hàm ở máy khác như gọi hàm local. Hợp đồng viết trong .proto, sinh code cho client và server; dữ liệu Protobuf binary (nhỏ, parse nhanh); chạy trên HTTP/2 nên có 4 kiểu gọi: unary, server streaming, client streaming, hai chiều. Đổi lại: debug bằng mắt khó, browser không gọi thẳng được (cần gRPC-Web + proxy).

Ví dụ
service OrderService {
  rpc GetOrder (GetOrderReq) returns (Order);          // unary
  rpc WatchOrders (Filter) returns (stream Order);     // server streaming
}
message GetOrderReq { int64 id = 1; }
Áp dụngChọn khi: service nội bộ gọi nhau dày đặc, cần độ trễ thấp, nhiều team cần hợp đồng chặt, cần streaming. Không chọn cho API public hay đối tác: họ cần gọi được bằng curl, nên dùng REST + OpenAPI.

⚠ BẫyĐổi số field trong .proto (= 1, = 2) là phá tương thích: client cũ đọc nhầm field. Chỉ thêm field mới, không đổi và không tái dùng số cũ.

Tự kiểmTrả lời trong 60 giây: “em chưa dùng gRPC” + hiểu biết + so với request–reply qua ActiveMQ (cùng dùng cho nội bộ; gRPC đồng bộ, nhanh, hợp đồng chặt; queue chịu được service chết tạm thời).

FVREST: startBackendRestful.js, SmartPos Open API, Swagger cho đối tác. gRPC: chưa dùng; giữa các service dùng request–reply qua ActiveMQ/STOMP.

Summary

REST là style: URL là tài nguyên, method là động tác, status là kết quả, stateless; GET/PUT/DELETE idempotent nên retry an toàn. gRPC là RPC với hợp đồng .proto, dữ liệu Protobuf binary, chạy trên HTTP/2 có streaming; hợp cho nội bộ cần nhanh, không hợp cho API public.

2GraphQL, webhook, chọn style

Q3 GraphQL là gì? Một ưu, một nhược? từ khóa: schema · resolver · over-fetching · N+1 · DataLoader

Client tự chọn field

Nôm naPhiếu gọi món: tick đúng món mình cần, bếp chỉ làm đúng mấy món đó, không thừa không thiếu.

ChốtMột endpoint, client gửi truy vấn chọn đúng field cần. Ưu: hết over-fetching (thừa dữ liệu) và under-fetching (phải gọi nhiều lần). Nhược: dễ dính N+1 query ở resolver, và khó cache HTTP vì mọi thứ là POST /graphql.

Ví dụLấy 20 đơn kèm customer { name } → resolver customer chạy 20 lần → 1 + 20 query. Sửa bằng DataLoader: gom 20 id thành một query WHERE id IN (…).
Áp dụngHợp làm BFF (backend for frontend) cho nhiều loại client (web, app) cần dữ liệu khác nhau. Backend fintech nội bộ ít khi cần.

⚠ BẫyClient gửi truy vấn lồng sâu tuỳ ý → một request làm sập DB. Phải giới hạn độ sâu và độ phức tạp truy vấn.

Tự kiểmNói trong 20 giây: một câu định nghĩa + một ưu + một nhược.

Q4 ⭐ Webhook là gì? Đối tác gọi webhook trùng thì xử lý sao? từ khóa: callback · at-least-once · idempotency key · HMAC signature · retry

Bên kia gọi ngược, có thể gọi trùng

Nôm naThay vì 5 phút gọi điện hỏi “xong chưa” một lần, mình để lại số; xong việc bên kia gọi báo. Họ không chắc mình đã nghe thì gọi lại lần nữa.

ChốtWebhook: bên có sự kiện chủ động gọi HTTP vào URL bên kia đã đăng ký. Đối tác thường gửi at-least-once: timeout là gửi lại → có thể trùng. Xử lý bằng idempotency theo id sự kiện hoặc id giao dịch, kiểm chữ ký, trả 2xx nhanh.

Ví dụ
nhận POST→kiểm chữ ký HMAC→INSERT event_id (unique)→mới: xử lý, trả 200trùng: trả 200, bỏ qua
Áp dụng
  • Unique constraint trên event_id / bill id là chốt chặn cuối; Redis SET NX chỉ là lớp chặn nhanh phía trước.
  • Đừng làm việc nặng trước khi trả 200: đối tác timeout sẽ gửi lại, tạo thêm trùng.

⚠ BẫySELECT “có chưa” rồi mới INSERT → hai request trùng tới cùng lúc đều thấy “chưa có”. Phải dựa vào unique constraint hoặc lock.

Tự kiểmNói trong 60 giây, có đủ hai chữ idempotency và at-least-once.

Q5 Thiết kế API mới thì chọn style nào? từ khóa: public API · internal · BFF · async callback · trade-off

Chọn theo ai gọi và họ cần gì

Nôm naGửi cho khách lạ thì dùng thư bưu điện chuẩn; nói với đồng nghiệp cùng phòng thì gọi nội bộ; ai cần báo khi xong thì để lại số.

ChốtKhông có style tốt nhất, chỉ có style hợp tình huống. Một hệ thường trộn: REST ra ngoài, gRPC hoặc queue bên trong, webhook báo đối tác.

Ví dụ
Tình huốngChọnVì sao
API cho đối tácREST + OpenAPIai cũng gọi được, tool sẵn
Service nội bộ gọi dàygRPCnhanh, hợp đồng chặt, streaming
Web + app cần dữ liệu khác nhauGraphQL (BFF)client tự chọn field
Báo kết quả việc xử lý lâuwebhookclient khỏi hỏi liên tục
Nội bộ, chịu được chậm, cần chịu lỗiqueue / eventbên nhận chết tạm vẫn không mất việc

⚠ BẫyTrả lời “GraphQL tốt hơn REST” hay ngược lại. Luôn nói kèm cái giá của lựa chọn.

Tự kiểmKể trong 30 giây 3 chỗ ở FV dùng 3 style khác nhau. (REST cho đối tác, request–reply qua queue nội bộ, IPN/webhook từ đối tác)

FVWebhook/IPN: Ministop IPN, IPN redirect ở payment webview SDK; chống trùng merchant bill id bằng idempotency, dedupe request trên Redis. GraphQL: chưa dùng.

Summary

GraphQL cho client tự chọn field, đổi lại dễ dính N+1 (sửa bằng DataLoader) và khó cache. Webhook là bên kia gọi ngược khi có sự kiện, gửi at-least-once nên phải idempotent theo id, dựa vào unique constraint. Chọn style theo người gọi: REST cho ngoài, gRPC/queue cho trong, webhook để báo kết quả.
