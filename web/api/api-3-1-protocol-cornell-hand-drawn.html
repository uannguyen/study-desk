3.1 · Protocol: framing, HTTP, WebSocket, broker

Quy ước nói chuyện trên transport: cắt message, kèm metadata, luật hỏi–đáp

1Protocol là gì, HTTP

Q1 ⭐ Protocol khác transport ở đâu? Có TCP rồi sao còn cần HTTP? từ khóa: application protocol · framing · header · status code · request–response

Transport chở byte, protocol cho byte ý nghĩa

Nôm naXe tải chở thùng tới nơi (TCP). Phiếu dán ngoài thùng ghi trong có gì, dài bao nhiêu, gửi trả lời về đâu (HTTP). Không có phiếu, người nhận mở ra chỉ thấy một đống đồ.

ChốtProtocol làm 3 việc TCP không làm: framing (message dài bao nhiêu), metadata (header, status), luật hội thoại (ai hỏi, ai đáp, khi nào đóng).

Ví dụ
POST /orders HTTP/1.1
Host: api.shop.vn
Content-Type: application/json
Content-Length: 13

{"amount":50}
Dòng trống = hết header; đọc đúng 13 byte = hết body. Đó là framing của HTTP/1.1.
Áp dụngChọn protocol theo kiểu hội thoại: hỏi–đáp → HTTP; hai chiều liên tục → WebSocket; gửi qua trung gian, hai bên không cần online cùng lúc → STOMP / AMQP / Kafka.

⚠ BẫyTài liệu thư viện hay gọi HTTP là “transport” (vd. “HTTP transport” của logger). Đó là nghĩa rộng; phỏng vấn nên nói rõ HTTP là protocol tầng ứng dụng, chạy trên TCP.

Tự kiểmKể 3 việc protocol làm mà TCP không làm. (cắt message, kèm metadata, luật hội thoại)

Q2 HTTP/1.1 và HTTP/2 khác nhau ở đâu? từ khóa: text vs binary · multiplexing · stream · HPACK · HOL blocking

Một hàng chờ → nhiều luồng chen nhau

Nôm naHTTP/1.1: một quầy, khách hỏi lần lượt, người sau chờ người trước. HTTP/2: vẫn một quầy nhưng nhận nhiều phiếu cùng lúc, phiếu nào xong trả trước.

ChốtHTTP/1.1 là text, mỗi kết nối mỗi lúc một request (browser mở khoảng 6 kết nối mỗi host để bù). HTTP/2 là binary frame có stream id → nhiều request song song trên một kết nối, và nén header (HPACK).

Ví dụ
HTTP/1.1HTTP/2
Định dạngtextbinary frame
Song songmở nhiều kết nốinhiều stream / 1 kết nối
Headergửi lặp lại nguyên vănnén HPACK
HOL blockingtầng HTTP và TCPchỉ còn tầng TCP
Áp dụngNgữ nghĩa giữ nguyên (method, status, header) nên code REST không đổi; thay đổi nằm ở server và load balancer. Thực tế thường để LB/CDN nói HTTP/2 với client, còn Node phía sau vẫn HTTP/1.1.

⚠ Bẫy“Bật HTTP/2 là mọi thứ nhanh hơn.” Mạng mất gói nhiều thì cả chục stream trên một TCP cùng bị HOL kéo chậm. Đó là lý do có HTTP/3 (xem 2.1, Q4).

Tự kiểmVì sao với HTTP/1.1 browser mở nhiều kết nối tới một host, còn HTTP/2 thì không cần? (1.1 mỗi kết nối chỉ chạy một request một lúc; 2 multiplex được)

FVREST/HTTP: startBackendRestful.js, gateway, SmartPos Open API. HTTP/2 chỉ dùng gián tiếp qua load balancer. Tự hỏi: LB đang nói HTTP/1.1 hay HTTP/2 với app mobile?

Summary

TCP chỉ chở byte; protocol cắt byte thành message, kèm metadata và đặt luật hỏi–đáp. HTTP/1.1 là text, một kết nối chạy một request một lúc; HTTP/2 dùng binary frame có stream id để chạy nhiều request trên một kết nối, nhưng vẫn còn HOL ở tầng TCP.

2WebSocket, broker, so sánh

Q3 ⭐ WebSocket là gì? Quan hệ thế nào với HTTP? từ khóa: HTTP Upgrade · 101 Switching Protocols · frame · full-duplex · ping/pong

Mở bằng HTTP, sau đó nói hai chiều

Nôm naGọi tổng đài (HTTP) xin nối máy. Nối xong, hai bên nói thẳng với nhau, ai muốn nói lúc nào cũng được, không cần hỏi trước.

ChốtWS mở đầu bằng một request HTTP có Upgrade: websocket; server trả 101, từ đó chính kết nối TCP đó chuyển sang frame WS hai chiều. Hết request–response: không có status code hay header riêng cho từng message.

Ví dụ
GET /ws + Upgrade→101 Switching Protocols→frame ⇄ frame→ping / pong giữ kết nối
Áp dụng
  • Message không có sẵn id hay status → app tự đặt: type, requestId để ghép hỏi–đáp, ack.
  • Kết nối sống lâu → cần heartbeat, tự reconnect; scale nhiều node phải tính sticky session hoặc pub/sub giữa các node.

⚠ BẫySocket.IO ≠ WebSocket. Socket.IO là protocol riêng chạy trên WS (có fallback polling); client WS thuần không nói chuyện được với server Socket.IO.

Tự kiểmVì sao WS qua proxy/firewall dễ hơn một giao thức TCP tự chế? (mở bằng HTTP trên port 80/443 như web thường)

Q4 STOMP, AMQP, Kafka là protocol hay là queue? từ khóa: broker · STOMP · AMQP · Kafka protocol · ack · reply-to

Broker là bưu cục, protocol là mẫu đơn

Nôm naActiveMQ, RabbitMQ, Kafka là bưu cục. STOMP, AMQP, Kafka protocol là mẫu đơn để nói chuyện với bưu cục đó.

ChốtBroker là phần mềm; protocol là cách client nói chuyện với broker trên TCP. Một broker có thể nói nhiều protocol (ActiveMQ: OpenWire, STOMP, AMQP, MQTT). Điểm chung: đi qua trung gian, có ack ở tầng ứng dụng.

Ví dụ
ProtocolDạng frameHay gặp với
STOMPtext, kết thúc bằng byte NULLActiveMQ, RabbitMQ (plugin)
AMQP 0-9-1binary, có độ dàiRabbitMQ
Kafkabinary, độ dài ở đầuKafka
Áp dụngRequest–reply qua broker: gửi kèm reply-to + correlation-id, bên kia trả về queue reply, bên gửi ghép theo id. Đổi lại: thêm độ trễ, trace khó hơn gọi HTTP thẳng.

⚠ Bẫy“Kafka là message queue như RabbitMQ.” Kafka là log lưu lại, consumer tự giữ offset và đọc lại được; RabbitMQ xoá message sau khi ack.

Tự kiểmA gửi qua ActiveMQ cho B đúng lúc B đang restart: chuyện gì xảy ra, so với gọi HTTP? (message nằm chờ trong queue; HTTP thì lỗi ngay)

Q5 ⭐ Bị hỏi “REST hay WebSocket?” thì trả lời thế nào? từ khóa: khác tầng · request–response · push · SSE · polling

Chỉnh câu hỏi trước, chọn sau

Nôm naGiống hỏi “đi xe tải hay ghi phiếu bằng tiếng Việt?”: hai thứ không cùng loại để chọn một.

ChốtREST là API style, WebSocket là protocol. So đúng là HTTP request–response vs kênh WS hai chiều. Chọn theo tiêu chí: một chiều hay hai chiều, ai chủ động, tần suất cập nhật.

Ví dụ
Nhu cầuChọn
Client hỏi khi cần (CRUD)HTTP + REST
Server đẩy một chiều (tiến độ export, thông báo)SSE
Hai chiều liên tục (chat, giữ ghế realtime)WebSocket
Cập nhật thưa, muốn hạ tầng đơn giảnpolling
Áp dụngCâu mở đầu: “Hai cái khác tầng, em tách ra thế này…”, rồi kể ca thật đã chọn và vì sao.

⚠ BẫyDùng WS cho mọi thứ “cho realtime” → mất cache HTTP, status code, retry sẵn có của HTTP; phải tự làm lại hết.

Tự kiểmNói trong 30 giây: vì sao export dùng SSE còn app mobile dùng WebSocket.

FVWS: fv-ccu.js (cổng WS cho app mobile, ack bằng sendUTF); Socket.IO cho giữ ghế realtime; SSE cho export. Broker: ActiveMQ/STOMP request–reply giữa các service, RabbitMQ (AMQP), Kafka cho thông báo trạng thái hoá đơn.

Summary

WebSocket mở bằng HTTP Upgrade rồi chuyển sang frame hai chiều trên cùng TCP; mất status và id sẵn có nên app tự đặt. STOMP, AMQP, Kafka là protocol để nói chuyện với broker, đi qua trung gian nên chịu được bên nhận tạm chết. “REST hay WS” là so khác tầng: chỉnh lại thành HTTP vs WS rồi chọn theo chiều và tần suất.
