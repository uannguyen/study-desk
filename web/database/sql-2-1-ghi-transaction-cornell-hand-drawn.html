Cú pháp SQL ② · Ghi dữ liệu và transaction

Ghi dữ liệu thì phải tính chuyện ghi nhầm và hai người ghi cùng lúc

1Ghi, transaction và lock

Q1 Thêm dữ liệu và lấy lại id vừa tạo thế nào? từ khóa: INSERT · RETURNING · INSERT…SELECT · ON CONFLICT

① INSERT: thêm dòng mới

Hiểu nôm naGửi thư ở bưu điện, nhân viên trả lại số biên nhận để sau này tra.

INSERT INTO users (name, email)
VALUES ('an', 'an@x.vn'), ('binh', 'binh@x.vn')
RETURNING id;

-- chép từ bảng khác
INSERT INTO wallets (user_id, balance)
SELECT id, 0 FROM users;

-- upsert: trùng khóa thì cập nhật
INSERT INTO wallets (user_id, balance) VALUES (1, 0)
ON CONFLICT (user_id)
DO UPDATE SET balance = EXCLUDED.balance;

Bên dướiRETURNING trả về dòng vừa ghi ngay trong câu đó, khỏi SELECT lại. EXCLUDED là dòng bạn định chèn. ON CONFLICT cần UNIQUE index trên cột đó.

⚠ BẫyKhông ghi tên cột (INSERT INTO users VALUES (...)) thì sau này thêm cột vào bảng là câu INSERT hỏng.

Q2 Sửa hoặc xóa dữ liệu sao cho không lỡ tay cả bảng? từ khóa: UPDATE · DELETE · WHERE · TRUNCATE

② UPDATE và DELETE: luôn có WHERE

Hiểu nôm naTrước khi xóa ảnh, nhìn lại đã chọn đúng ảnh chưa. Lỡ bấm "chọn tất cả" là mất hết.

-- 1. Xem trước sẽ chạm vào dòng nào
SELECT * FROM wallets WHERE id = 1;

-- 2. Rồi mới sửa / xóa với đúng điều kiện đó
UPDATE wallets SET balance = balance + 1000
WHERE id = 1;
DELETE FROM transactions
WHERE created_at < now() - interval '2 years';

-- xóa sạch bảng, reset id (dùng khi seed lại lab)
TRUNCATE transactions RESTART IDENTITY;

Bên dướipsql in ra UPDATE 1, DELETE 340: số dòng bị chạm. Số khác với dự kiến là dấu hiệu viết sai điều kiện.

⚠ BẫyUPDATE wallets SET balance = 0; không có WHERE vẫn chạy và áp lên mọi dòng. Không có nút undo, trừ khi đang ở trong transaction.

Tự kiểmChạy một UPDATE sau BEGIN, xem kết quả, rồi ROLLBACK. Dữ liệu có quay về không?

Q3 ⭐ Transaction là gì, viết thế nào? từ khóa: BEGIN · COMMIT · ROLLBACK · atomicity · autocommit

③ Transaction: tất cả hoặc không gì cả

Hiểu nôm naChuyển 500k từ ví An sang ví Bình: trừ An và cộng Bình phải cùng xảy ra. Mất điện giữa chừng thì coi như chưa chuyển.

BEGIN;
UPDATE wallets SET balance = balance - 500 WHERE id = 1;
UPDATE wallets SET balance = balance + 500 WHERE id = 2;
COMMIT;   -- hoặc ROLLBACK; để hủy cả hai

Bên dướiTrước COMMIT, phiên khác vẫn thấy dữ liệu cũ. Một câu lỗi làm hỏng cả transaction: mọi câu sau báo "current transaction is aborted" cho tới khi ROLLBACK.

⚠ BẫyKhông có BEGIN thì mỗi câu tự commit riêng (autocommit). Hai UPDATE tách rời, câu thứ hai lỗi là tiền mất.

Tự kiểmMở hai psql. Phiên 1: BEGIN + UPDATE, chưa COMMIT. Phiên 2 SELECT thấy số dư cũ hay mới?

Q4 ⭐ Hai request cùng trừ tiền một ví: chặn thế nào? từ khóa: SELECT FOR UPDATE · row lock · lost update · deadlock

④ FOR UPDATE: khóa dòng trước khi sửa

Hiểu nôm naHai người cùng rút tiền một sổ tiết kiệm: người đến sau phải đợi người trước rút xong mới được xem số dư.

BEGIN;
SELECT id, balance FROM wallets
WHERE id IN (1, 2)
ORDER BY id      -- khóa theo thứ tự id cố định
FOR UPDATE;
-- Node kiểm tra đủ tiền, rồi:
UPDATE wallets SET balance = balance - 500 WHERE id = 1;
UPDATE wallets SET balance = balance + 500 WHERE id = 2;
COMMIT;

Bên dướiKhóa giữ tới hết transaction. Ai muốn sửa hoặc FOR UPDATE cùng dòng phải chờ; SELECT thường vẫn đọc được nhờ MVCC.

⚠ BẫyHai transaction khóa 2 ví theo thứ tự ngược nhau thì chờ nhau mãi: deadlock. Postgres phát hiện và hủy một bên. Khóa theo thứ tự id cố định thì hết.

Tự kiểmGiải thích vì sao khóa theo thứ tự id cố định thì không thể xảy ra deadlock.

Q5 Xem và đổi isolation level của một transaction? từ khóa: READ COMMITTED · REPEATABLE READ · SERIALIZABLE · snapshot

⑤ Isolation level: được nhìn thấy gì

Hiểu nôm naĐang làm bài kiểm tra: bạn có được thấy bạn bên cạnh vừa sửa đáp án không? Mức cách ly quyết định chuyện đó.

SHOW transaction_isolation;   -- mặc định: read committed

BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT balance FROM wallets WHERE id = 1;
-- phiên khác UPDATE + COMMIT ở đây
SELECT balance FROM wallets WHERE id = 1;  -- vẫn số cũ
COMMIT;

Bên dướiRead Committed: mỗi câu lấy snapshot mới, hai lần đọc có thể khác nhau. Repeatable Read: cả transaction dùng một snapshot. Serializable: như chạy lần lượt, xung đột thì báo lỗi để bạn retry.

⚠ BẫyPostgres không có dirty read ở mức nào: Read Uncommitted chạy như Read Committed.

Tự kiểmChạy lại đoạn trên với READ COMMITTED. Lần SELECT thứ hai ra số nào?

Q6 Không muốn khóa thì viết optimistic lock thế nào? từ khóa: optimistic lock · version · rowCount · retry

⑥ Optimistic lock: ghi kèm số phiên bản

Hiểu nôm naSửa chung một tài liệu: lúc lưu, nếu ai đó đã lưu bản mới hơn thì bạn bị báo "bản của bạn đã cũ, tải lại rồi sửa".

-- đọc kèm version, giả sử nhận về version = 7
SELECT balance, version FROM wallets WHERE id = 1;

UPDATE wallets
SET balance = 500, version = version + 1
WHERE id = 1 AND version = 7;
-- UPDATE 0 → có người sửa trước → đọc lại, retry

Bên dướiKhông ai phải chờ ai. Chỉ lúc ghi mới kiểm tra version; ở Node đọc rowCount (pg) hoặc affected (TypeORM) để biết có cần retry.

⚠ BẫyTranh chấp cao (nhiều request vào cùng một ví) thì retry liên tục, chậm hơn FOR UPDATE. Optimistic hợp khi xung đột hiếm.

Tự kiểmKhi nào chọn FOR UPDATE, khi nào chọn version? Nói trong 30 giây.

Summary

Trước UPDATE/DELETE, chạy SELECT với cùng WHERE; thiếu WHERE là áp lên cả bảng. Nhiều câu phải cùng thành công thì bọc trong BEGIN … COMMIT. Hai request sửa cùng dòng: FOR UPDATE (chờ nhau, khóa theo thứ tự id để tránh deadlock) hoặc cột version (không chờ, xung đột thì retry). Postgres mặc định Read Committed và không bao giờ có dirty read.

Hành vi isolation theo tài liệu Postgres mục Transaction Isolation; ví dụ dùng schema lab.
