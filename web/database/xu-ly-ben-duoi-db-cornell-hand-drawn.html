Bên dưới một database chạy thế nào?

Postgres, MongoDB, Redis: server viết bằng C/C++ + B-tree, cache RAM, WAL, MVCC

1Đường đi của một query

Q1 DB thực chất là gì? Code Node nói chuyện với nó ra sao? từ khóa: server process · wire protocol · driver · connection pool

① Một server chạy mãi, nghe trên cổng TCP

Hiểu nôm naBạn không tự vào kho lấy sách, bạn đưa phiếu qua cửa sổ cho thủ thư.

Bên dướiPostgres (C) mỗi connection 1 process; Mongo (C++) mỗi connection 1 thread; Redis (C) 1 thread chạy lệnh. Driver đóng gói query theo protocol rồi gửi qua TCP.

Ví dụCổng 5432 · 27017 · 6379; protocol riêng của Postgres · BSON · RESP.

⚠ BẫyMở connection mới mỗi request: tốn handshake, Postgres tốn cả 1 process. Phải dùng pool.

Q2 ⭐ Một câu query đi qua những bước nào bên trong DB? từ khóa: parser · planner/optimizer · executor · EXPLAIN

② Đọc phiếu → chọn đường → đi lấy

Hiểu nôm naThủ thư đọc phiếu, nghĩ xem lục kệ hay tra mục lục nhanh hơn, rồi mới đi lấy.

Bên dướiParser biến SQL thành cây (như V8 ra AST) → planner ước lượng chi phí từng cách dựa trên thống kê, chọn rẻ nhất → executor chạy plan, gọi xuống storage.

Ví dụEXPLAIN in ra Seq Scan hay Index Scan; Mongo explain() ra COLLSCAN hay IXSCAN.

⚠ BẫyCó index chưa chắc được dùng: thống kê cũ hoặc lọc ra quá nhiều dòng thì planner chọn quét cả bảng.

Tự kiểmĐọc một plan và nói nó chọn đường nào, vì sao.

Q3 Vì sao cùng một query lúc 1ms, lúc 50ms? từ khóa: page · buffer pool · shared_buffers · cache hit/miss

③ Dữ liệu nằm theo trang, trang nóng giữ trong RAM

Hiểu nôm naSách hay đọc để sẵn trên bàn; sách ít dùng phải vào kho lấy.

Bên dướiBảng = file chia page 8KB (Postgres). Cần page nào thì tìm trong RAM trước (shared_buffers, WiredTiger cache). Có = hit, không có = miss, đọc đĩa chậm hơn hàng trăm lần.

Ví dụLần đầu chạy sau restart chậm (cache lạnh), lần hai nhanh (đã nằm trong RAM).

⚠ BẫyBenchmark một lần rồi kết luận; dữ liệu lớn hơn RAM thì hit ratio tụt, query chậm đột ngột.

Tự kiểmNói được "working set vừa RAM" nghĩa là gì.

Q4 ⭐ Index B-tree hoạt động thế nào? Vì sao nhanh? từ khóa: B-tree · O(log n) · composite index · leftmost prefix

④ Mục lục lùn và bè: 3–4 bước là tới

Hiểu nôm naTra mục lục: chữ cái → trang → dòng, không lật từng trang.

Bên dướiMỗi node là một page chứa hàng trăm key đã sắp xếp. Cây rất lùn: 100 triệu dòng chỉ sâu ~3–4 tầng, tức đọc ~4 page. Key sắp xếp nên dùng được cho =, khoảng, ORDER BY.

Ví dụIndex (user_id, created_at) dùng được cho WHERE user_id = ?, không dùng được cho chỉ WHERE created_at > ?.

⚠ BẫyIndex không miễn phí: mỗi lần ghi phải cập nhật thêm mọi index.

Tự kiểmVẽ được cây 3 tầng và giải thích luật leftmost prefix.

FVMongo là DB chính, Redis làm cache. Tự hỏi: service nào set maxPoolSize bao nhiêu, collection lớn nhất có index gì?

Summary

DB là server process; driver gửi query qua TCP nên phải dùng connection pool. Bên trong, query được parse, planner chọn đường rẻ nhất, executor đọc page qua buffer pool trong RAM. Index B-tree lùn và bè nên chỉ cần vài page là tới dòng cần tìm; nhanh hay chậm phụ thuộc page có sẵn trong RAM không.

Q5 ⭐ Commit xong mà mất điện thì có mất dữ liệu không? từ khóa: WAL · journal · fsync · checkpoint · durability

⑤ Ghi nhật ký trước, sửa dữ liệu thật sau

Hiểu nôm naĐổi gì cũng ghi vào sổ trước; mất điện thì sáng mai đọc sổ làm nốt.

Bên dướiSửa page trong RAM → ghi thay đổi vào WAL (append, tuần tự nên nhanh) → fsync → mới báo commit OK. Page bẩn được ghi xuống đĩa sau, ở checkpoint. Crash thì replay WAL.

Ví dụPostgres: WAL. Mongo: journal của WiredTiger. Redis: AOF, mặc định everysec nên có thể mất ~1 giây.

⚠ BẫySo tốc độ ghi khi một bên không chờ fsync, bên kia có chờ: so sai.

Tự kiểmNói được vì sao ghi WAL tuần tự nhanh hơn ghi thẳng từng page.

Q6 Đang có người đọc thì người khác ghi có phải chờ không? từ khóa: MVCC · snapshot · row version · VACUUM · bloat

⑥ MVCC: mỗi người đọc thấy một bản chụp

Hiểu nôm naSửa bài thì viết sang tờ mới; bạn đang đọc tờ cũ vẫn đọc tiếp.

Bên dướiPostgres UPDATE không ghi đè mà tạo phiên bản mới của dòng, đánh dấu transaction nào thấy bản nào (xmin/xmax). Đọc không chặn ghi. Bản cũ hết ai dùng thì VACUUM dọn.

Ví dụBảng update liên tục mà autovacuum không theo kịp → bảng phình (bloat), query chậm dần.

⚠ BẫyMVCC không chống được hai người cùng ghi một dòng: vẫn cần lock hoặc SELECT … FOR UPDATE.

Tự kiểmGiải thích Read Committed và Repeatable Read bằng "bản chụp lúc nào".

Q7 Redis khác gì hai thằng kia mà nhanh vậy? từ khóa: in-memory · hash table · single thread · event loop · O(1)

⑦ Redis bỏ đĩa, bỏ planner: chỉ còn hash table trong RAM

Hiểu nôm naThủ thư chỉ dùng mặt bàn, không có kho: lấy cực nhanh nhưng bàn nhỏ.

Bên dướiGET user:42 = hash key, nhảy thẳng tới ô nhớ, O(1). Không parser SQL, không planner, không page. Một thread chạy lệnh trên event loop như Node: không cần lock, mỗi lệnh tự atomic.

Ví dụINCR làm counter, SET key val NX EX 30 làm lock: an toàn vì lệnh chạy tuần tự.

⚠ BẫyGiống Node: một lệnh chậm (KEYS *, HGETALL hash khổng lồ) chặn cả server.

Tự kiểmNói được vì sao Redis single-thread mà vẫn chịu được hàng chục nghìn lệnh/giây.

FVTự hỏi: Redis ở FV đang lưu gì (cache, session, lock)? Bật RDB hay AOF? Mất 1 giây dữ liệu có sao không?

Summary

Commit an toàn nhờ ghi WAL/journal tuần tự và fsync trước khi báo OK; crash thì replay WAL. MVCC giữ nhiều phiên bản dòng nên đọc không chặn ghi, đổi lại phải VACUUM. Redis bỏ đĩa và planner, chỉ còn hash table trong RAM với một thread, nên nhanh nhưng phải đánh đổi độ bền và dung lượng.

Số tầng B-tree, page 8KB là bậc độ lớn/mặc định của Postgres; Mongo (WiredTiger) cùng nguyên lý nhưng khác chi tiết.
